# Stack-agnostic core with stack packs picked by detection

## Context and Problem Statement

[0004](0004-one-template-shared-files-conditional-per-stack-files.md) built one template around a closed `stack` question (Express, Next.js, bare React Native) with `{% if stack %}` blocks. The owner now wants the template to serve any modern TypeScript project in an app ecosystem: web (Next.js, Astro, SvelteKit, Solid), mobile (bare React Native and Expo) and backend (Elysia, Hono, Fastify, Express, Nest.js). A closed list with Jinja blocks per stack cannot grow to that, and most of what the template gives (protocols, review loop, git rules, decision records, the `check` contract) does not depend on the framework. The Task 2 family (TASK-2, 2.1 to 2.5) was written for three stacks only. The usual flow stays: scaffold the project with the framework's own tool, then apply this template over it (README, [0014](0014-generated-projects-use-backlog-md-and-ignore-local.md), TASK-2.5).

## Considered Options

- Keep the closed `stack` list and add a branch per framework: every new framework edits shared files, and the list grows without end.
- One template per stack: duplicates the core and needs several update runs per project (the reason 0004 rejected it).
- A generic core plus a small pack per framework, picked by a post-copy script that reads `package.json` and copies the pack: works, but Copier does not track the copied file, so `copier update` never refreshes it (the objection 0004 raised against overlay scripts), and it adds a script and a Python call.
- A generic core plus a pack per framework, with detection in the `stack` question's own default (Copier's built-in `_external_data` reads `package.json`) and the pack rendered by Copier.

## Decision Outcome

Chosen option: "detection in the `stack` default, pack rendered by Copier", because Copier then tracks the pack and `copier update` refreshes it, nothing runs outside Copier for detection, and adding a framework is a pack file, a line in a precedence list, its scripts and dev dependencies and any config files it needs (where those live is TASK-2.5's to decide: tasks in `copier.yml` conditioned on `stack`, data in the pack, or conditional file names).

- **Generic core:** everything Copier renders that does not depend on the framework (today, or as Phase 1 adds it): `AGENTS.md`, protocols, `.claude/`, docs, the foundations config files of [0036](0036-config-files-extend-the-projects-own-instead-of-overwriting-it.md) and the `check` contract (`typecheck`, `lint`, `format:check`, `test`, `check`).
- **Pack:** one file per framework in `packs/` at the root of the template repository, beside `template/` and so never copied as such, plus `packs/generic.md`. `template/docs/stack.md.jinja` includes the project's pack and falls back to the generic one. Copier resolves includes from the template's root, not from `template/`. Because Copier renders `docs/stack.md`, it tracks it. A pack holds a few rules, the framework's prepare step before typecheck, and how the framework meets each part of the contract. The stack-specific `{% if stack %}` blocks of `template/AGENTS.md.jinja` move into packs; `AGENTS.md` keeps one line naming the stack and pointing at `docs/stack.md`, and its router table says when to read it. Packs are Jinja templates (Copier renders them), so code samples containing `{{`, `{%` or `{#` are wrapped in `{% raw %}`. The generic pack names no framework tools: it says that no tools are chosen and points at `docs/protocols/done.md`, so a project without a pack still gets the protocols and the names of the contract.
- **Detection:** the `stack` question keeps its name and becomes free text (no `choices`). Its default is computed in Jinja from `package.json` through `_external_data`: the first name in a fixed precedence list found in `dependencies` or `devDependencies` wins (Expo before React Native, Next.js before Express, and so on; SvelteKit lists `@sveltejs/kit` in `devDependencies`); no match, or no `package.json`, gives `generic`. A name in the list with no pack file renders the generic pack, so Phase 1 can list Expo (before React Native) without shipping an Expo pack, and an Expo project is not given the bare React Native rules, which forbid Expo packages. The answer is stored in `.copier-answers.yml`, so `copier update` does not detect again.
- **Override and names:** `-d stack=<name>` (or answering the question) replaces detection. Pack names are the framework slugs; `express`, `next` and `rn` keep their present names so answers already stored stay valid. A name with no pack file renders the generic pack and the answer is kept as typed.
- **Framework files Copier must create:** a framework with no TypeScript scaffolder (Express) has its starter files shipped by the template under conditional file names (folders too, so no empty `src/` appears), which is 0004's mechanism kept for that case only. The condition is a second question, `skeleton` (boolean, stored in the answers), whose default is true only when the framework has no TypeScript scaffolder and the project has no `package.json` yet at the first copy. The default must test `stack` before it reads `package.json` (`stack == 'express' and not <package.json>`, in that order), because the condition is what lets `-d stack=<name>` alone avoid the YAML abort for other frameworks (reproduced: with the operands swapped it aborts). An existing Express project therefore keeps its own `package.json` and `src/`, even when the copy uses `--overwrite`, and `copier update` keeps the stored answer.
- **Journeys, Phase 1:** Next.js: scaffold with `create-next-app`, then copy the template over it with `--overwrite` (the scaffold writes its own `AGENTS.md`, and without `--overwrite` a non-interactive copy stops at the conflict); detection picks `next`. Bare React Native: scaffold with the community template, then copy; detection picks `rn`. Express, new project: start from an empty folder and copy with `-d stack=express` (or answer the question), because an empty folder has no `package.json` to detect; the skeleton ships with it. Express, existing project: copy over it; detection picks `express` and `skeleton` is false because a `package.json` exists.
- **Post-copy tasks:** only scripts, dev dependencies (`npm pkg set`, `npm i -D`) and lines appended to an ignore file (TASK-23 adds `.env`), run on copy only or made idempotent (TASK-2.5 decides). No detection, no pack copying and no other edits to the project's own files in tasks. The generic pack defines no scripts, so a project on it (no `package.json`, or a framework that has no pack yet, such as Expo in Phase 1) gets none; the check fallback of `docs/protocols/done.md` applies, and so does any CI that runs `npm run check` only where that script exists (TASK-27).
- **Per-pack config files:** a lint, format or test config that must differ per framework is the same open point as per-pack scripts. TASK-2.5 decides and records where it lives: conditional file names on `stack`, under names that never match a scaffold's own files (0036), or files rendered from a pack folder. A foundations config that is framework-independent (the `tsconfig` of 0036) needs none.
- **Scope:** which frameworks get a pack, and which are verified for v0.1.0, is not decided here. Phase 1 ([doc-1](../../backlog/docs/doc-1%20-%20Phase-1-plan-Usable-v0.1.0.md)) names Next.js, bare React Native and Express; the other packs are follow-up work (TASK-2.6). "Solid" in the owner's list is read as SolidStart until the owner says plain Solid with Vite is meant too.

### Consequences

- Good, because a changed pack reaches existing projects through `copier update`, and the detected stack is visible as a normal answer.
- Good, because a new framework needs no change to the rendered shared files (a pack file, a precedence line in `copier.yml`, its scripts and dev dependencies, and any config files it needs), and an unknown or pack-less one still gets the whole generic core.
- Good, because it works over any scaffold whose `package.json` is readable as YAML and never overwrites the framework's own configs (0036).
- Bad, because Copier reads `package.json` as YAML, which rejects tab indentation (Biome's default, and probably SvelteKit's scaffold): the first copy then aborts with a YAML error. `-d stack=<name>` avoids it for a framework with a scaffolder; an existing Express project also needs `-d skeleton=false`, because the `skeleton` default reads `package.json` too. `copier update` works because the stored answers are used. Reproduced in review rounds 2 and 4 and in a scratch run for this record.
- Bad, because stack rules now load when an agent opens `docs/stack.md`, not on every read of `AGENTS.md` ([0007](0007-agent-instructions-live-per-project-as-a-thin-agents-md-router.md) kept them inline so every agent sees them). The one-line pointer and the router row soften this. Rules that refer to "this file", such as keeping the `nextjs-agent-rules` block ([0014](0014-generated-projects-use-backlog-md-and-ignore-local.md)), must name `AGENTS.md` once they move into a pack.
- Bad, because the precedence list lives in `copier.yml` as one long Jinja default and needs upkeep.
- Findings the packs and TASK-2.1 to 2.4 must carry: a pack declares a prepare step that runs before `tsc` (shown needed for Next.js, `next typegen`; Astro `astro sync` and SvelteKit `svelte-kit sync` are their frameworks' equivalents, to verify in TASK-2.6); `typescript` may be missing from a scaffold (Astro's minimal template) and must be ensured as a dev dependency; `tsc` does not check `.astro` or `.svelte` files, so a pack may name the framework's own checker next to `typecheck`; Expo projects also list `react-native`, hence the precedence rule.

## More Information

- Supersedes [0004](0004-one-template-shared-files-conditional-per-stack-files.md); it also replaces the inline `{% if stack %}` blocks that [0007](0007-agent-instructions-live-per-project-as-a-thin-agents-md-router.md) kept (0007's router idea stands). Builds on [0036](0036-config-files-extend-the-projects-own-instead-of-overwriting-it.md).
- Evidence (2026-10-02, Copier 9.18.2 on Windows, three throwaway spikes in scratch folders, since deleted).
  - Spike 1, real scaffolds from the then-current `create-next-app` (Next.js 16), `create-astro` and `sv create`: the overlay replaced Next.js's `AGENTS.md`, left `tsconfig.json` untouched, added the foundations file and a `typecheck` script; `tsc -p tsconfig.foundations.json --noEmit` exited 0 on all three, with the framework's own settings (`strict`, `moduleResolution`, `verbatimModuleSyntax`, `jsx`) kept and the two added flags applied. The `extends` chains were a plain config (Next.js), a package config (`astro/tsconfigs/strict`) and a generated one (SvelteKit). Next.js failed `LayoutProps` not found until `next typegen` had run, and failed identically on its own `tsconfig.json`; Astro needed `typescript` installed. This spike detected the framework with a Python post-copy script; it worked, including from a temporary git clone, but its pack file was not tracked by Copier, so it was replaced after review.
  - Spike 2, detection and update: a template whose `stack` default is computed from `package.json` with `_external_data`, packs in `packs/`, rendered by `docs/stack.md.jinja`. Over projects holding only a hand-written `package.json` (not the real scaffolds), Hono, Next.js, Astro, Expo (which also lists `react-native`), dev-dependency-only Express and Next.js plus Express picked the expected pack; an unknown dependency, a `package.json` without dependencies and an empty folder gave `generic`; Fastify, which had no pack file, kept the answer `fastify` and rendered the generic pack; `-d stack=express` overrode detection; `-d stack=nonsense` rendered the generic pack. After `copier copy --vcs-ref v1.0.0` and a later `copier update --vcs-ref v2.0.0` in a git project, `docs/stack.md` showed the changed pack, and the stored `stack` answer stayed `hono` although `package.json` had gained `next` in between.
  - Spike 3, the skeleton: a `skeleton` boolean question defaulting to `stack == 'express' and not (the project's package.json)`, with conditional file and folder names. An existing Express project (its own `package.json` and `src/app.ts`) copied with `--defaults --overwrite` kept both files and stored `skeleton: false`; an empty folder with `-d stack=express` got `package.json` and `src/app.ts` and stored `skeleton: true`; an empty folder with defaults got `generic`, no skeleton and no empty `src/`. Re-run by the round-4 reviewer in a mini template: `copier update` over a project that has the skeleton kept `skeleton: true` and applied a changed skeleton file; a tab-indented Express project aborted with `-d stack=express` alone and copied and updated cleanly with `-d stack=express -d skeleton=false`; a tab-indented Next.js project copied with `-d stack=next` alone.
- Not checked: an existing project with no `tsconfig.json` (a JavaScript-only Express app: the foundations file would extend a missing file; outside Phase 1, see TASK-18); where per-pack scripts, dev dependencies and config files live (no spike exercised them; TASK-2.5 decides); whether `sv create` and Biome-formatted projects write tab-indented `package.json` files; an interactive (prompted) copy with the computed default; detection on the `package.json` files of real scaffolds (the Phase 1 scaffolds are expected to use spaces; TASK-2.5 criterion 5 verifies it); real scaffolds of Expo, bare React Native, Nest.js, Hono, Fastify, Elysia and SolidStart (only their `package.json` shape was used); macOS and Linux; a monorepo (only the root `package.json` is read); a project that gains its `package.json` after the first copy (the answer should stay as stored until changed with `-d stack=<name>` on `copier update`).
